# 50体・100体での負荷原因分析

検証ブランチ `perf/100-pawns` の50体を使用。main・公開版とゲームロジックは変更していない。計測用スクリプト・結果のみ追加した。対策前の原因分析であり、最適化の適用ではない。

## 確認できた原因

### 食料探索に失敗すると毎更新で全域経路探索を繰り返す

`main.ts` は固定1/60秒のシミュレーション更新ごとに全員の `updateNeeds` を呼ぶ。`needs.ts` は満腹度20%以下・食事ジョブなしの場合、食料候補を列挙し `findPaths` で到達先を探す。候補があっても目的地を決められなければ、ジョブを作らずfalseを返す。失敗時の再試行間隔や結果の記録がないため、次の更新で同じ探索を行う。仕事選択の `decisionSeconds` とは別経路で、既存の仕事選択間隔では抑制されない。

50体のシミュレーション79〜82秒（3秒分、180更新）を計測した。後半で一斉に空腹になる。

| 診断カウンター | 回数 |
| --- | ---: |
| 食料の経路探索開始 | 5,192 |
| 目的地を選べず終了 | 5,182 |
| 食料候補数の合計 | 5,192 |
| 地形の全域探索・キャッシュミス | 4,953 |
| キャッシュヒット | 288 |
| キャッシュの追い出し | 4,916 |

候補が1つはあるのに、ほぼすべての探索が失敗している。単に食料候補がゼロで即座に戻っている状況ではない。目的地判定にはポーンの占有・予約も含まれる。個々の失敗の内訳（食料マスと隣接マスのどこが誰に占有されていたか）は今回のカウンターでは計測していない。

`calls=10,482` は占有フィルター用ラッパーからの再帰呼び出しも数えるため、全域探索数ではない。実際の地形キャッシュへの照会数はヒットとミスの合計5,241。

### 16件の経路キャッシュが人数に足りず、再利用前に追い出される

`pathfinding.ts` は出発マスごとに32×32全域のDijkstra探索結果を保持するが、同じ通行ルールあたり16出発点まで。50体・100体が異なる場所から順番に照会すると、前の更新の結果が次の更新まで残らない。

キャッシュミス率は約94.5%（4,953 / 5,241）。失敗探索の反復とキャッシュ容量不足が組み合わさっている。探索時は、到達マスごとのMap・経路getter・ヒープなども毎回作り直す。

### CPUプロファイルで経路探索とGCに集中

productionバンドルを非圧縮で生成し、GPU描画なし、同じ79〜82秒をChrome DevTools ProtocolのCPU Profilerで測定。プロファイルなしの前回の数値とは、ビルド・計測オーバーヘッド・区間が異なる。

| 処理 | サンプル時間 | 総サンプル時間に対する割合 |
| --- | ---: | ---: |
| 食料探索からのfindPaths（子処理込み） | 約11.63秒 | 約87.6% |
| 通行判定からのWalls.at（自身の処理） | 約6.23秒 | 約46.9% |
| ガベージコレクション | 約1.41秒 | 約10.6% |

総サンプル時間約13.28秒。Walls.atはfindPathsの子処理なので、表の割合は合算しない。建造物が少なくても、隣接マス・斜め通過判定のたびに文字列キーで建造物Mapを参照するため、この関数に時間が集まる。まず呼び出し元の大量再探索を抑える方が有効で、見た目やGPUシェーダーが空腹区間の主因という結果ではない。

## 切り分け実験

ゲームルール・乱数シード・人数・測定区間をそろえ、**キャッシュ上限だけを一時的に16から128へ変更**した。

| 条件 | 79〜82秒の処理時間 |
| --- | ---: |
| 元の16件 | 13,223ms |
| 一時的な128件 | 564ms |

約23倍の差。終了時は両方とも50体生存・49体空腹・7体移動中・HP100%など、記録した状態は同じだった。キャッシュの追い出しが大きな要因であることを裏付ける。

128件を正式な対策として保存してはいない。キャッシュは1件あたり全域のデータを持つため、容量を増やす対策にはメモリ量・無効化・100体時の確認が必要。また、容量を増やしても毎更新の無駄な食料探索自体は残る。

## 自由行動の引っ掛かり

空腹前の4〜7秒も別にプロファイルした。3秒分の処理は約196ms、そのうちプレイヤーの `updateRoaming` 配下の経路探索に約100msのサンプルが集まった。自由行動は5秒ごとで、同じ初期状態の多数ポーンの探索が同時期に走る。空腹の毎更新探索とは別に、自由行動の探索が一度に集中する問題がある。GPU描画時間はこの測定に含めない。

## 改善する順序

1. 食料探索失敗時に短い再試行待ちを入れ、毎更新の再探索をやめる。満腹感・飢餓ダメージは今までどおり毎更新し、手動の食事指示を待たせない。食料追加・占有変化の後に探索を再開することも確認する。
2. 多数の出発マスを扱えるよう、経路キャッシュの保持件数とメモリ構造を調整する。単に無制限に保持しない。建造物・植物・扉の変化による既存の無効化を維持する。
3. 自由行動などの新規探索を更新間に分散し、同じフレームへの集中を減らす。
4. 元と同じ50体・100体の180秒比較で、空腹区間の処理時間・最大更新時間・GC後のメモリ・食事と睡眠の動作を確認する。必要な回帰確認を厳選し、人数別の単体テストを大量追加しない。

```sh
npx vite build --base=./ --minify=false --sourcemap

```
