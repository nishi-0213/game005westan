# 長い壁の迂回と探索の分割実行

検証ブランチ `perf/100-pawns`。比較元は `678d9d7`。ゲームのマップは32×32、初期100人のまま。320×320は独立した経路探索試験で使用する。

## 実装

- 最初の256マスは通常のA*で探す。64×64以上で探索が長引いた場合、16×16マスの区画に分けた階層探索に切り替える。近くの目的地では階層図を作らない。
- 区画内を上下左右の通行可能な成分に分け、区画境界の全ての通路で成分を接続する。区画間の経路を探した後、その経路と隣接する成分内でマス単位のA*を行う。通行・斜めの角抜け・停止禁止の判定は維持する。階層経路が使えない場合は通常A*を続ける。
- 区画間の結果を最大128組保持し、同じ成分間の探索に再利用する。壁・家具などの完成／破壊では該当区画を再構築し、結果キャッシュを破棄する。プレイヤー用と敵・野生用は別の図を持ち、扉の開閉は敵・野生側だけを更新する。
- 部屋の領域判定は引き続き到達不可能な対象の除外に使う。部屋・移動領域の再分類自体は従来どおり全体更新であり、区画図の部分更新とは別。
- 移動命令と自由移動の経路計算を待ち行列に入れ、表示フレームごとに合計約2ms、最大4096ステップまで進める。同時に計算途中の探索は4件までとし、32ステップ単位で交代する。順番待ちの目的地も予約するので、複数選択時の目的地は重複しない。
- 途中の通行マスを渡りきって安全なマスで待機してから計算する。新しい命令・中断・除去では待ち行列から取り消す。壁や扉の通行条件が変わった探索はやり直す。
- 既存の「内部番号に応じた60更新に1回」の自動探索開始タイミングは維持する。開始済みの計算はフレーム共通予算で進める。一時停止中は進めず、3倍速でも表示フレームあたりの予算は増やさない。
- 目的地指定の探索では、通過する全マスについて経路オブジェクトを生成せず、目的地の結果だけを生成する。

全ての検索を非同期にしたわけではない。仕事・素材などの最寄り対象を探す段階探索、一部の逃走先・配置先の列挙、複数人の移動先候補の全マス生成・整列には同期処理が残る。温度やゲーム内マップの拡大は今回の対象外。

## 測定方法と結果

Node 24、AMD EPYC、利用可能CPU4。同一環境で前後それぞれ3回、各回8経路。最初の1経路と、構築後の残り7経路の平均を分けて記録する。各経路の到着点・隣接関係・障害物・斜めの角抜けを検証した。

壁はほぼ南北全長を塞ぎ、下端近くに1マスの隙間を開ける。区画境界に沿う壁と、境界から5マスずらした壁を比較した。生データは [hierarchy-scaling.json](performance/hierarchy-scaling.json)、再測定は `node scripts/benchmark-hierarchy.mjs <比較元のソースを展開したディレクトリ>`。

| マップ | 条件 | 初回 前→後 ms | 構築後 前→後 ms | 構築後の倍率 |
| --- | --- | ---: | ---: | ---: |
| 32×32 | 近場 | 0.433→0.303 | 0.048→0.019 | 2.60倍 |
| 32×32 | 長い壁 | 1.665→1.801 | 1.054→0.701 | 1.50倍 |
| 320×320 | 近場 | 0.987→1.121 | 0.005→0.005 | 1.11倍 |
| 320×320 | 長い壁 | 138.938→41.078 | 129.015→29.578 | 4.36倍 |
| 320×320 | 境界からずれた壁 | 130.548→26.295 | 135.095→24.253 | 5.57倍 |

近場と32×32では階層探索を使わない。微小な時間差にはJIT・GCなどの変動を含み、通常マップ全体が数倍高速になるという結果ではない。

区画経由の経路は最短経路を保証しない。今回の320×320では、正確なA*に対して最大2.67%／4.44%長くなった。これは測定した配置の値で、全ての地形での上限ではない。

## 100件の重い移動命令

同じ320×320の長い壁を迂回する100件を同時に予約し、分割処理を待機時間なしで連続実行した。異なる出発点・目的地を使い、全件の完成経路を検証している。

命令の受付は1.48ms、分割処理の合計は3.74秒。1684回に分け、1回あたりp95は3.91ms、最大38.67msだった。最初の完成は91回目、50件完成は963回目、全件完成は1684回目。60FPSならそれぞれ約1.5秒／16.1秒／28.1秒相当になる。

フレーム数からの換算は60FPSで毎フレーム1回進めた場合の目安であり、実際の描画込みの経過時間を測定したものではない。FPSが低いと待ち時間はさらに長くなる。全員の長距離命令が瞬時に完成する実装ではなく、画面の一括停止を避けながら順に進める実装。区画間をまたぐ詳細経路そのものの共有などは今後の改善余地。

2msは厳密な上限ではない。256マスの区画再構築、初回の移動領域分類、経路復元、メモリ回収は途中で分割できないため、予算を超える回がある。

## 通常の100人ゲーム

32×32、乱数シード42、productionビルド。自由行動優先で180秒分を描画なしで処理。描画ありは自由3倍速、5秒ウォームアップ後に約10秒測定。前後各1回のため、小差は高速化の確証としない。描画はSwiftShaderによるソフトウェアWebGLで、実機のFPSではない。

| 条件 | 前 | 後 |
| --- | ---: | ---: |
| 180秒分のCPU処理 | 2.257秒 | 2.125秒 |
| 更新平均 | 0.208ms | 0.196ms |
| 更新p95 | 0.400ms | 0.400ms |
| 更新最大 | 20.900ms | 59.100ms |
| GC後JSヒープ | 9.615MiB | 9.533MiB |
| 描画あり・更新平均 ms | 3.959 | 4.221 |
| 描画あり・更新p95 ms | 9.300 | 12.000 |
| 描画あり・更新最大 ms | 24.300 | 34.600 |
| 描画あり・FPS | 10.095 | 8.695 |

描画ありは今回、後の方が低いFPSとなった。通常32×32の描画性能の改善は確認できていない。更新時間の最大値も後が大きく、階層探索によって全ての一時的な停止が消えるわけではない。

生データ：[シミュレーション前](performance/hierarchy-before-simulation.json)／[後](performance/hierarchy-after-simulation.json)、[描画あり前](performance/hierarchy-before-browser.json)／[後](performance/hierarchy-after-browser.json)。

描画なしの終了時は前後とも99人生存、位置99種類、収集済み40個、最低HP約50%。自由行動の経路計算を後回しにするため、移動中の人数や位置の経過は一致しない。描画ありの測定終了時は前後とも100人生存。JavaScriptエラーはなかった。

テストは追加2件に絞り、迂回経路・壁の破壊と建設・勢力別の扉・予算分割・目的地予約・変更時の再探索・指示の中断と差し替え・除去時の取消を検証した。既存を含む270件とproductionビルドが成功。
